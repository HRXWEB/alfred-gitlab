从一个真实工作问题开始

一个 MR 同时改了请求参数、缓存发布和测试。人工只看 diff 容易漏掉跨文件约定；你想先让 AI 找异常路径和接口回归，再由维护者做最终判断。

01 · 同一个 @GitLabDuo，可能是两种评审

能力Code Review Flow传统 GitLab Duo Code Review
方式Agentic；结合相关文件与跨文件依赖非 Agentic；主要基于 MR 和文件差异
执行记录创建评审 Session不创建 Code Review Flow Session
授权 / 用量使用 Agent Platform 与 Credits通常要求 Duo Enterprise 席位
如何辨别查看 MR Activity 和 AI → Sessions没有对应 Flow Session 时核对管理员配置

上游默认路由会考虑发起用户是否有 Duo Enterprise 席位。群组可配置统一使用 Flow；19.3 相关切换能力已 GA。JH 的路由与计费规则应由管理员确认，不能只从 reviewer 名字推断。

02 · 第一次手动请求评审

  1. 完成 平台、Code Review 流程与 Runner 准备。Code Review Flow 的 Runner 需支持 Docker 镜像并使用 gitlab--duo 标签。
  2. 进入 Code → Merge requests，打开已有实际代码差异的 MR。
  3. 在 Reviewers 中指派 @GitLabDuo，或在评论中提交下方 quick action。
  4. 到 AI → Sessions 检查是否创建了评审任务；回到 MR 查看 summary 和逐行评论。
  5. 对有疑问的评论回复并提及 @GitLabDuo，要求解释相关调用链或举出可复现输入。
MR 评论 · 请求一次评审
/assign_reviewer @GitLabDuo
追问示例
@GitLabDuo 请解释这个空列表分支会如何影响多 host 缓存，并给出可复现输入。

03 · 教它审查本项目的约定

在 .gitlab/duo/mr-review-instructions.yaml 中维护评审规则，通过 MR 审核并合入项目。规则应具体指向可检查的行为；“保证代码质量”太宽泛。

YAML · 项目评审规则
instructions:
  - name: 缓存与 host 隔离
    fileFilters:
      - "src/**/*.py"
    instructions: |
      检查网络异常时是否保留旧缓存。
      检查不同 host 的项目与凭据是否仍然隔离。
      如指出问题，请描述触发条件并引用相关代码。
  - name: 回归测试
    fileFilters:
      - "tests/**/*.py"
    instructions: |
      分页改动应覆盖多页数据和中途失败。
      检查测试是否验证用户行为，而不只是重复实现。
AGENTS.md 不是评审规则文件固定 19.3.3 文档明确说明：Code Review Flow 不读取 AGENTS.md 或 SKILL.md。Developer Flow 的开发约定和 Code Review 的审查规则应分别配置。规则是 AI 上下文，不是强制执行的权限或合规策略。

观察带有规则名称的评审反馈，确认文件 pattern 命中了预期文件。群组规则可指定一个模板项目，在 Settings → General → GitLab Duo features → Customize code review 中选择；项目规则与群组规则可以组合使用。

04 · 稳定后再开自动评审

  1. 维护者进入 Settings → Merge requests → GitLab Duo Code Review。
  2. 选择 Enable automatic reviews by GitLab Duo 并保存。
  3. 先用小范围试点确认频率、噪声与用量；草稿和无差异 MR 不会按同样方式自动触发。
  4. 若要排除机器人或特定分支，在默认分支维护下方配置。排除规则只控制自动评审，不阻止人工请求。
YAML · 19.3 GA 的自动评审排除规则
# .gitlab/duo/mr-review-automated-rules.yaml
exclude:
  source_branches:
    - "dependabot/*"
  authors:
    - "*-bot"

05 · 怎么使用评审结果

把 AI 评论分类为“可复现缺陷、值得讨论的设计、可以忽略的噪声”。修复明确问题；对模糊结论要求依据。没有发现问题的 summary 不代表测试通过，更不表示 MR 应当自动合并。

  • 检查 MR 是否过大，关键上下文可能因限制被截断；优先拆成可审查的小 MR。
  • 在一个 MR 中回复“以后记住这个规则”不会自动成为全项目长期约定；长期规则写入专用 YAML。
  • 没有 Session 时，确认运行的是传统评审还是 Flow，再排查 Runner。
  • 极狐当前文档中的中文增强评审另有扩展行为；未核实 striding 19.3.3 的实际实现，不将其当作已启用能力。
