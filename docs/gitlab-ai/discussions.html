把一条评审意见变成代码修改

19.3 正式可用的 Resolve with GitLab Duo，处理的是代码与讨论，不只是关闭线程。

19.3 GA基于 Developer Flow
01 · 哪种评论适合交给它02 · 前置条件03 · 点击路径04 · 自动关闭之后仍要验收
从一个真实工作问题开始

评审者指出“第二页请求失败时不能发布半份缓存”，你已经同意，但还要切回编辑器、改代码、补测试、提交再回到 MR。这个流程可以直接从评审线程发起。

01 · 哪种评论适合交给它

适合目标明确、修改范围可控、能够测试验证的评论。例如提取重复校验、修正异常处理、补充边界测试。若讨论仍在决定 API 设计或存在两种业务解释，应先由人确认方案。

评论是否适合直接执行
“这里不好，优化一下”先细化：具体触发条件、期望行为和限制。
“第二页失败时抛出异常，不发布新缓存，并增加回归测试”适合，目标与验收清晰。
“删掉鉴权能让这个测试通过”先审查需求与安全设计，不能把测试变绿当作完成。

02 · 前置条件

需要 Developer、Maintainer 或 Owner 角色，启用 Agent Platform 和 Allow foundational flows → Developer，有可用 Runner，push rules 允许服务账号提交。MR 的源分支也必须允许相关写入。

这个操作会产生代码提交Resolve with GitLab Duo 会读取评审评论及上下文，修改源分支并提交推送，随后回复摘要并解决线程。点击前应确认线程中的实现要求已经达成一致。

操作依据：Resolve a discussion with GitLab Duo · 固定 19.3.3 文档 ↗

03 · 点击路径

  1. 打开 MR，找到仍未解决的具体评审线程，补充必要上下文和验收条件。
  2. 在 Resolve thread 旁点击下拉箭头，即 More resolve options。
  3. 选择 Resolve with GitLab Duo。这与普通 Resolve thread 只是标记讨论结束的行为不同。
  4. 打开 AI → Sessions 查看执行；回到 MR 检查新增提交、diff、自动回复和线程状态。
在线程中补充的执行要求
请保持现有公开函数签名。
只在所有项目分页均成功后发布新缓存。
增加第二页返回 HTTP 错误的测试，并验证旧缓存仍可读取。
不要修改 host 注册和凭据迁移逻辑。

04 · 自动关闭之后仍要验收

  1. 检查新提交是否真的解决了评论描述的问题，而不只是改了变量名或更新说明。
  2. 核对新增测试是否在失败路径上运行，查看对应 CI 结果。
  3. 若实现不符合要求，重新打开线程，说明遗漏的触发条件或预期行为。
  4. 需要更广泛的 MR 修改时，使用 Developer Flow 的明确提及，避免把大量无关任务塞进一条行内评论。
找不到菜单时优先检查 Developer 流程开关、项目角色、Runner 与源分支写入权限。19.3 的功能历史仍提及 resolve_discussion_with_duo 控制，私有实例若有自定义功能标志应由管理员核对。
