让外部 Agent 在 GitLab 事件中执行

区分本地 MCP 接入与 Runner 中的外部 Agent，按实例支持情况选择。

高级路线JH 可用性需管理员 / 厂商确认
01 · 两种接入不能混为一谈02 · 先确认实例是否支持这条路线03 · 实例已有集成时，维护者这样启用04 · 自建集成时，需要哪些工程工作05 · 第一轮只验收一个闭环
从一个真实工作问题开始

你想在 Issue 评论里提及某个外部 coding agent，让它在 CI 环境中完成任务并回写 MR。与“本地客户端通过 MCP 读 GitLab”相比，这需要平台管理执行身份、模型连接和触发器。

01 · 两种接入不能混为一谈

问题本地 Agent + MCPGitLab external agent
谁开始执行你在客户端发起GitLab 事件 / 提及触发
在哪里跑本地或客户端所在环境平台安排的 CI/CD 执行环境
模型认证客户端已有的模型账号按外部 Agent 集成配置的凭据或网关
产物位置本地修改或 MCP 写入资源MR / Issue 回复与平台 Session
适合个人开发上下文接入团队事件驱动的异步开发任务

如果只是希望现有客户端读取 MR，优先完成 MCP 接入。外部 Agent 不是绕过平台授权或直接复用个人本地会话的捷径。

02 · 先确认实例是否支持这条路线

固定 19.3.3 上游文档列出外部 Agent 能力，但同时说明其受功能标志与已验证客户条件控制，可能需要联系 GitLab 支持启用；并明确 external agents 不适用于 Duo 自部署模型形态。极狐发行版的支持范围、模型和配置应向实例管理员或厂商确认。

  • 满足 Agent Platform 条件，开启 flow execution 与 external agents。
  • Runner 能访问对应模型服务、GitLab 和必要镜像。
  • 集成在该实例已注册，并能在 AI Catalog 或项目中看到。
  • 明确模型凭据来源、服务账号权限和触发事件；不能把 JihuLab.com 或 GitLab.com 的托管入口直接照搬到私有化实例。

操作依据：外部 Agent 条件与自部署限制 · 固定 19.3.3 文档 ↗

03 · 实例已有集成时，维护者这样启用

  1. 在 AI Catalog 或项目的 AI → Flows 中找到管理员已提供的 external agent 集成。核对名称、版本和预期模型服务。
  2. 按集成要求配置项目的 CI/CD Variables 或网关认证。字段名随集成不同；凭据使用对应受控入口，不写进评论或 YAML 正文。
  3. 点击 Enable 选择测试项目，配置 Mention / Assign 等实际支持的触发事件。
  4. 查看该集成生成或绑定的 service account，在一个测试 Issue 中提及其真实用户名，给出明确的编码任务。
  5. 到 AI → Sessions 与相关 pipeline 查看执行，最终检查评论、MR 和实际测试结果。
评论示例 · 用户名来自实例配置
@<实际外部-agent-服务账号> 请先分析本 Issue 的分页缺陷。
只修改请求与相关测试，不更改认证或部署配置。
完成后创建草稿 MR，说明实际测试结果与未验证事项。

04 · 自建集成时，需要哪些工程工作

管理员和维护者需要按官方 external agent schema 准备镜像、执行命令和模型连接，注册到 AI Catalog，配置复合身份与触发器。通过 Catalog 启用时可自动创建相应服务账号；手工接入则应按官方要求配置项目对应身份，不直接让所有仓库共用一个高权限个人 PAT。

组成需要验证的结果
镜像和命令容器能启动 Agent，工具链正确，工作目录可运行项目测试。
模型连接使用被支持的模型端点和凭据方式，不假设 localhost 可访问。
执行身份任务按触发用户与服务账号的有效权限执行，分支规则仍生效。
事件与回写提及只触发预期任务，结果回复到正确 Issue / MR。

这里不提供一个“通用可直接运行”的外部模型 YAML：各集成的入口、认证变量和镜像不同，伪造统一配置会让读者在认证与权限处失败。应从实例实际启用的官方集成定义开始修改。

05 · 第一轮只验收一个闭环

以一个低耦合任务验证“提及 → Session → Runner → 草稿 MR → 测试”。若集成不在 Catalog 中，先找管理员确认支持状态；不要通过复制互联网命令、临时放开变量保护或放宽分支权限来试出一个未知配置。
