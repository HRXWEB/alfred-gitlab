把模糊需求整理成可实施的工作项

使用 Planner 先澄清范围、拆分验收条件，再交给 Developer Flow 编码。

Planner Agent编码前的需求准备
01 · 打开 Planner02 · 先让它分析，不急着创建工作项03 · 复核后再创建或更新04 · 依赖分析与验收
从一个真实工作问题开始

需求只有一句“提高项目搜索体验”，直接交给编码 Agent 很容易做成无边界重构。先用 Planner 把用户问题、约束、依赖和验收条件写清楚，再选择其中一项实施。

01 · 打开 Planner

先启用 foundational agents。进入项目或群组，在右侧 Duo 侧栏选择 Add new chat → Planner。在 IDE 中可从 Agent Platform 的 Chat 新会话下拉菜单选择 Planner；可见范围取决于项目授权与默认 namespace。

操作依据：Planner 入口与前置条件 · 固定 19.3.3 文档 ↗

02 · 先让它分析，不急着创建工作项

Planner 提示词 · 示例
我们要改善多 GitLab host 的项目搜索体验。
范围：搜索准确性、刷新反馈、个人页面导航。
约束：保留 Python 3.9 与现有 Alfred 命令，不改凭据存储方式。
请先读取项目已有 Issue，找重复需求与依赖。
输出不超过 5 个可独立实施的任务，每项包含用户场景和验收条件。
先给草稿，不创建、不关闭任何 Issue。

提供真实项目或 Issue URL，以及排序标准。不要让“优先级”只来自模型猜测；明确用户影响、实施成本和依赖关系。

03 · 复核后再创建或更新

  1. 检查拆分结果是否互相独立，是否有重复 Issue，是否包含实际可验证的验收条件。
  2. 选择一项明确任务，让 Planner 创建指定类型的 Issue / task，或更新已存在的工作项。
  3. 核对标题、正文、标签、里程碑和关联关系，避免在错误群组或项目中创建。
  4. 把确定的任务交给 Developer Flow；保留需要人决定的产品问题，不把它们藏进编码提示词。
确认后的明确写入任务
请只把上面“刷新失败反馈”这一项创建为当前项目的 Issue。
保留已有验收条件，关联到我给出的父任务。
其他任务暂时不创建，也不要修改已有 Issue 的状态。

04 · 依赖分析与验收

Planner 可以分析工作项、标签、里程碑和依赖关系；部分图关系能力依赖额外启用的 Orbit。striding 未核实该能力时，先使用明确的 Issue 链接和可读取关系，不假定它具备整个组织的完整知识图谱。

  • 每个任务对应一个用户问题，而不只是一个文件名。
  • 验收条件包含边界、失败行为和必要兼容要求。
  • 依赖与负责人来自真实项目事实；未知信息明确标注。
  • 创建后的工作项可由人直接交给开发者，无需重新猜测意图。
