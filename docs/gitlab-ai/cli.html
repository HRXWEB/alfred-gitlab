在终端中使用 Duo，并复用团队技能

先完成认证与一次本地任务，再使用 19.3 的实验插件机制打包重复操作。

CLI 19.2 已 GA插件 9.10.0 起为 Experiment
01 · 用 glab 启动，减少重复认证02 · 也可以使用独立 duo 命令03 · 先计划，再改代码04 · 把重复工作装成插件05 · 做一个团队插件，先从一条命令开始06 · 版本不匹配时怎么处理
从一个真实工作问题开始

你习惯终端开发，希望在仓库里询问实现、规划修改、运行测试；团队还希望把 MR review 或发布说明这类固定流程复用起来。Duo CLI 与插件解决的是这两个层次的问题。

01 · 用 glab 启动，减少重复认证

固定 19.3.3 的安装文档要求 GitLab 19.2 以上、满足 Agent Platform 条件，自部署实例还要允许 Duo CLI。通过 glab 使用时，文档要求 glab ≥ 1.107.0；CLI 本体版本与服务端版本应分别核对。

Shell · 以真实实例替换示例域名
glab auth login --hostname gitlab.example.com
glab duo cli

在 glab 的交互认证中选择适用方式。首次启动时按提示安装 Duo CLI binary。不要把旧的 npm 安装教程与当前 binary 分发混用；这里不自动执行安装，也不为 striding 假定认证方式。

操作依据：CLI 安装与认证前提 · 固定 19.3.3 文档 ↗

02 · 也可以使用独立 duo 命令

安装官方 binary 后运行 duo，按首次设置输入实例 URL 与具备 api scope 的 PAT。若系统已认证的 glab 可用，支持的 duo 版本可使用它作 credential helper。密钥只填入对应认证入口，不写入团队共享示例。

Shell · 独立客户端路径
duo
# 已完成初始配置后，可编辑本地认证设置：
duo config edit

自动化环境可使用受保护的凭据注入 GITLAB_TOKEN 与 GITLAB_BASE_URL。不应在 shell 脚本或文档中保存实际 token。

03 · 先计划，再改代码

  1. 在目标仓库目录启动 Duo CLI。检查提示符下的当前模式。
  2. 用 Tab 切到 Plan 模式，要求先解释代码与修改计划。Plan 是只读；默认 Build 模式可读写。
  3. 核对方案和修改范围后切换 Build，明确要求实施、运行测试并汇报结果。
  4. 通过工具审批检查终端与文件操作；需要停止当前任务时按 Esc。
两阶段提示词 · 示例中的注释不是 CLI 指令
先分析项目缓存刷新流程，列出导致部分数据发布的可能路径。
不要改代码。提出一个保持 Python 3.9 兼容的最小修复计划。

# 确认计划并切换 Build 后，再发送：
按刚才的计划实施，复用已有测试。
运行测试并列出实际结果；不要提交或推送未经我检查的变更。

04 · 把重复工作装成插件

19.3 引入的插件能力从 Duo CLI 9.10.0 起为 Experiment。插件可以组合 Agent Skills、自定义 slash commands 和 MCP servers；市场是这些插件的目录。先检查 duo plugin --help 与实际 CLI 版本。

Shell · 先确认官方市场实际存在 mr-review 插件
duo plugin marketplace list
duo plugin marketplace show gitlab-duo-plugins
duo plugin install mr-review@gitlab-duo-plugins
duo plugin list

首次使用插件时会自动注册官方市场。安装前用 marketplace show 核对名称；市场内容可能变化。重启 CLI 后技能和命令才会被发现，是否需要显式调用以插件说明为准。

scope作用范围适用情形
user个人所有项目，默认范围个人常用技能。
project.gitlab/duo/plugins.json，可提交仓库团队约定且所有人需要的插件。
local.gitlab/duo/plugins.local.json个人当前项目配置，应纳入忽略规则。

操作依据：插件、市场与安装范围 · 固定 19.3.3 文档 ↗

05 · 做一个团队插件，先从一条命令开始

先把稳定的任务说明写成自定义命令或 Skill，测试几次，再将它与所需 MCP 配置打包进插件。插件市场的目录结构、manifest 和变量名与 CLI 版本关联，按固定版本参考编写，避免套用 19.4 以后的新规范。

团队技能的任务正文示例
发布说明任务约定：
1. 读取最近两个 tag 之间的提交与相关 MR。
2. 按用户可见行为归类，不虚构影响范围。
3. 标注 breaking changes、迁移步骤和验证状态。
4. 先输出草稿，不自动创建 release。
5. 对缺失的 Issue 或测试证据明确标注未知。

插件不是安全沙箱。它定义或加载的 MCP 工具仍按各自授权执行。团队共享配置应审查来源、版本与新增能力。

06 · 版本不匹配时怎么处理

19.3 发布说明与固定文档对 glab 包装层的插件命令写法存在不同示例，本章统一使用独立 duo plugin … 语法；glab 包装层以本机 glab duo --help 为准。不要因为服务端升到 19.3，就假定本地客户端也自动具备插件子命令。
