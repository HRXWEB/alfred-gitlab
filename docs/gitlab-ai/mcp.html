让现有 coding agent 连接 striding

配置 OAuth 与 MCP，把 Issue、MR、讨论和 CI 日志带进你正在使用的开发工具。

MCP 在 19.3 仍为 Beta19.3 增强 MR 工具

从一个真实工作问题开始

你已经在本地 Agent 中写代码，但每次都要手动复制 MR 描述、评审意见和失败日志。MCP 可以让客户端按权限直接获取这些资源，减少上下文搬运。它提供工具接口，不提供模型。

01 · 先理解这条调用链

01 · 客户端你使用的 AI 开发工具
02 · OAuth授权客户端访问 striding
03 · MCP调用 /api/v4/mcp
04 · GitLab按你的权限返回资源

外部客户端的模型账号、费用与工具审批仍由客户端决定；GitLab 端决定数据访问权限。不要把 Alfred 里的 PAT 当作 MCP 的默认认证配置，也不要把 MCP 开通理解为 Duo 编码流程已经开通。

02 · 19.3 的管理员前置条件

固定 19.3.3 文档要求检查三项：Duo availability 设为 Always on 或 On by default、开启 Beta / 实验功能、允许访问 MCP Server。19.2 虽已把 MCP 扩展到 Free 档位，19.3 文档仍保留上述开关要求。若新版文档只列出一项开关，不应直接倒推到这个版本。

  1. 管理员核对实例的 Duo availability 与 Beta / 实验开关。
  2. 在 Admin → Settings → General 的可见性与访问控制配置中，查找允许 MCP Server 访问的设置；中文标签以 JH 管理界面为准。
  3. 确认客户端能访问实例 HTTPS URL，认证回调可正常到达，企业证书链受信任。
  4. 若禁用了 OAuth Dynamic Client Registration，应先由管理员预注册带 mcp scope 的 OAuth 应用，并确认客户端支持配置该 client ID。

操作依据：19.3 MCP 的开关、认证与客户端配置 · 固定 19.3.3 文档 ↗

03 · 示例 A：Cursor 通过 HTTP 连接

  1. 打开 Settings → Cursor Settings → Tools & MCP。
  2. 在 Installed MCP Servers 中新增服务器，将下面配置添加到 mcp.json。替换为真实实例域名；若 GitLab 部署在子路径中，保留该前缀。
  3. 保存，等待浏览器打开 OAuth 授权页；没有弹出时重新启动客户端并检查连接状态。
  4. 确认授权的实例与账号正确，批准后回到客户端查看工具列表。
JSON · 用真实 striding URL 替换示例域名
{
  "mcpServers": {
    "striding": {
      "type": "http",
      "url": "https://gitlab.example.com/api/v4/mcp"
    }
  }
}

04 · 示例 B：Claude Code / stdio 客户端

Shell · Claude Code 示例
claude mcp add --transport http striding https://gitlab.example.com/api/v4/mcp

在 Claude Code 中完成连接与浏览器授权。若客户端只支持 stdio，可使用下方代理配置；这条路线需要 Node.js ≥ 20。不同客户端的配置文件格式不相同，不能把 JSON 原样塞进任意客户端的配置。

JSON · 仅对支持这种格式的 stdio 客户端使用
{
  "mcpServers": {
    "striding": {
      "command": "npx",
      "args": ["mcp-remote", "https://gitlab.example.com/api/v4/mcp"]
    }
  }
}

05 · 用一个真实 MR 验证连接

  1. 先让客户端列出可用 GitLab 工具，确认连接成功，而不是只看到“服务器已添加”。
  2. 给出一个你有权限访问的完整 MR URL，要求只读获取描述、讨论与流水线状态。
  3. 要求它解释未解决的评论和失败测试，再决定是否允许修改本地代码。
  4. 修改完成后检查本地 diff 与测试。创建 MR、发表评论等写入操作，应看清客户端将调用的具体工具。
提示词 · 首次只读验证
先只读取这个 MR，不发表评论、不改 GitLab 数据：
https://gitlab.example.com/team/app/-/merge_requests/42

整理目标、未解决讨论和失败流水线。
请读取真正的代码 patch，再指出需要修改的本地文件。
区分“接口已经返回的事实”和“还需要验证的推断”。

06 · MR 工具的细节，决定上下文是否完整

工具 / 参数19.3 中要注意的行为
list_merge_requests19.3 新增；按项目、作者、assignee、reviewer、状态、标签、搜索词等筛选。
get_merge_request19.3 增强为支持 MR URL 和关联数据；不带 include 只返回基本 MR。
include每次最多请求一个 facet，例如 notes、commits 或 pipelines；不是一次带任意多种上下文。
include: ["diffs"]返回差异统计，不是完整 patch 文本；真正审代码应再调用 get_merge_request_diffs。
list_duo_sessions19.3 提供任务会话查询；不包含 Duo Chat 会话。
“读到了 MR”不代表“读到了代码差异”如果 Agent 只基于标题或增删行统计做 review，应明确要求获取 patch。早先页面里“一个请求拿齐 diff、讨论和流水线”的描述过于简化，这里按固定版本工具契约展开。

操作依据：MR 工具参数、facet 限制与 patch 工具 · 固定 19.3.3 文档 ↗

07 · 排障与多实例命名

症状排查
能打开网页，MCP 却 403MCP 访问开关、Beta / 实验开关、账号权限与 Duo availability。
OAuth 注册失败DCR 是否禁用、管理员是否预注册应用、客户端是否支持对应 OAuth 配置。
只有部分工具或 MR 无法读取比较实例返回的实际工具集合和账号资源权限；JH 可能有差异。
多个 GitLab 的工具名称冲突可使用 X-Gitlab-Mcp-Server-Tool-Name-Prefix 为该实例设置前缀。
证书或网络失败安装正确 CA、检查代理与实例子路径，不应直接关闭 TLS 验证。

在 Agent 中读取他人创建的 Issue 和评论时，内容应作为任务数据而非新的操作指令。先用可信测试项目验证读写边界，再扩大使用范围。
