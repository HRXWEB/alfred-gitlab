MR 冲突了，让 Duo 协助合并

从冲突入口发起自动处理，检查生成提交是否同时保留两侧业务意图。

19.3 GA需要源分支推送权限
01 · 先确认这个冲突支持网页处理02 · 从 MR 的冲突提示发起03 · 没有冲突标记，不等于业务正确04 · 失败时如何继续
从一个真实工作问题开始

你的分支增加了缓存异常处理，目标分支同时调整了刷新接口。简单选 ours 或 theirs 会丢掉一侧修改。你希望 AI 先结合上下文处理，再由你确认最终行为。

01 · 先确认这个冲突支持网页处理

该入口面向 GitLab UI 可以解决的冲突。不是所有 Git 冲突都可在网页中处理；过于复杂的冲突仍应回到本地。用户需具备 Developer 以上角色、源分支 push 权限，并满足 Agent Platform 条件。

自动处理会推送到源分支Duo 会分析冲突、编辑文件、提交并推送，再在 MR 上发布摘要。它尊重分支保护规则，不会通过 force-push 绕过受保护分支。

操作依据：GitLab Duo 冲突处理范围与权限 · 固定 19.3.3 文档 ↗

02 · 从 MR 的冲突提示发起

  1. 进入 Code → Merge requests，打开冲突 MR，选择 Overview。
  2. 在合并检查区域找到冲突条目。可直接点击 Resolve with GitLab Duo，或先进入 Resolve conflicts 再选择该按钮。
  3. 查看 Session 或 MR 活动，等待处理完成；不要同时在另一个客户端向同一分支提交相互冲突的修改。
  4. 阅读生成的摘要和提交 diff，确认冲突已消失，并运行覆盖两侧修改的测试。
验收清单 · 示例
验收时重点检查：
- 目标分支的新接口参数是否保留？
- 本分支的异常缓存保护是否仍然存在？
- 相关调用点是否一并调整？
- 旧测试与新增回归测试是否都通过？

03 · 没有冲突标记，不等于业务正确

Git 能合并只说明文本层面可以组成一个提交。比如 AI 保留了一个新参数，却漏掉相应的异常回退逻辑，MR 仍可能“可合并但有缺陷”。应比较源分支和目标分支各自的需求，再检查最终文件与测试。

  • 确认没有为了消除冲突删掉另一侧的新功能。
  • 检查锁文件、迁移、配置与生成文件是否需要使用各自工具重新生成。
  • 若两侧设计本身互斥，先确定业务方案，再人工合并。
  • 不满足 UI 范围或权限时，用本地 Git 解决；不要为了使用 AI 临时放宽分支保护。

04 · 失败时如何继续

没有入口先查冲突类型、角色与功能开关；推送被拒绝查看分支规则；任务给出无法可靠处理的结论时保留分析，在本地分支继续。需要更细粒度的编码协作，可使用 IDE Agentic Chat；需要明确平台任务，可提及 Developer Flow。
