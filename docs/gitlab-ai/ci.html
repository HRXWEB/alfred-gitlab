流水线失败：从“解释日志”到“提出修复”

区分单作业问答、Fix CI/CD Pipeline Flow 与 CI Expert，知道建议会出现在哪里。

Fix CI/CD Pipeline19.3 前已具备
01 · 根据目标选择工具02 · 在 MR 或流水线页面运行修复03 · 19.3 中的结果不是“总会新建 MR”04 · 为分析补齐有效上下文05 · CI Expert：先讨论配置方案06 · 修复后的验收
从一个真实工作问题开始

MR 在 CI 里失败，本地却通过。日志很长，你需要先知道是测试、依赖、镜像还是配置问题，再决定是否要修改仓库。不要直接把“让 CI 变绿”当作完整目标。

01 · 根据目标选择工具

目标入口结果
只解释一个错误Chat 中提供具体作业日志与上下文原因、证据、排查建议；不等于已经修复。
分析并提出代码修复Fix pipeline with DuoMR 内建议、修复 MR，或无法修复的说明。
讨论流水线结构或配置方案CI Expert AgentCI/CD 配置分析和建议；仍需校验真实环境。

02 · 在 MR 或流水线页面运行修复

  1. 确认已有失败 pipeline，启用 Allow foundational flows → Fix CI/CD Pipeline，具备 Developer 以上权限，并配置 Runner 与服务账号提交权限。
  2. MR 场景：进入 Code → Merge requests → Overview，在失败流水线下点击 Fix pipeline with Duo；也可在 MR 的 Pipelines 标签页使用同名入口。
  3. 非 MR 场景：进入 Build → Pipelines，打开失败流水线，在右上角点击 Fix pipeline with Duo。
  4. 到 AI → Sessions 查看分析，完成后回到 MR 或流水线检查产物。

操作依据：运行路径、权限和执行条件 · 固定 19.3.3 文档 ↗

03 · 19.3 中的结果不是“总会新建 MR”

场景预期产物
失败流水线关联现有 MR，修复在当前 diff 内通常在原 MR 提供行内 code suggestions，由你审查应用。
需要改动当前 MR diff 之外的文件可能创建新的修复 MR。
失败流水线没有关联 MR创建包含修复的新 MR。
证据不足、敏感或不适合自动修复可能只给出分析与下一步说明。
修正旧版指南中的过度概括Fix Pipeline 的 MR 内行内建议模式在 19.2 已 GA；19.3 不应一概描述成“自动新建修复 MR”。没有新 MR 时，先检查原 MR 的建议与评论。

操作依据：不同 pipeline 上下文的输出行为 · 固定 19.3.3 文档 ↗

04 · 为分析补齐有效上下文

Chat 或任务说明示例
请分析这个失败的 pipeline，先给出原因和证据。
重点区分：工具链版本不一致、依赖缺失、真实代码缺陷。
不要通过跳过测试、删除断言或设置 allow_failure 来绕过问题。
如果修复涉及默认分支以外的文件，请说明需要哪些变更。
最终列出修复后的验证方法与尚未验证的环境假设。

固定版本文档说明，AI 网关只处理作业日志尾部约 150 KiB。错误如果出现在很长的安装输出之前，Agent 可能看不到真正原因。可减少无用输出，在作业末尾保留错误摘要，或拆分过大的作业；不要只靠重复执行同一个修复。

操作依据：日志上限与诊断限制 · 固定 19.3.3 文档 ↗

05 · CI Expert：先讨论配置方案

在项目的 Duo 侧栏中选择 Add new chat → CI Expert。提供当前 .gitlab-ci.yml、依赖的 include、Runner 类型和目标，例如“只在相关目录变更时运行集成测试”。让它解释规则命中顺序与潜在漏跑场景，再把方案放进 MR 验证。

操作依据：CI Expert 入口和适用场景 · 固定 19.3.3 文档 ↗

06 · 修复后的验收

应用建议或打开修复 MR 后，重新运行失败作业和相关测试。确认变绿来自真正修复，而不是减少测试范围、忽略错误或隐藏日志。环境权限、密钥、外部依赖故障应由相应维护者处理，不能靠修改业务代码掩盖。
