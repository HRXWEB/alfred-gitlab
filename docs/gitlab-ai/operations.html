管理 Agent 的执行、可见性、模型与用量

使用 19.3 的任务计划展示、Restricted 可见性和 Credits 上限，把试点结果变成可管理的团队能力。

从一个真实工作问题开始

团队已经能发起 Agent 任务，接下来关心的是：它现在做到哪一步、为什么停住、谁能复用流程、模型在哪里运行，以及哪些自动任务正在消耗额度。

01 · 看懂 Session，而不是只等最后一条评论

  1. 进入项目 AI → Sessions，选择对应任务。
  2. 检查目标、状态与活动记录。19.3 在会话详情侧栏直接展示最新任务计划和进度，减少逐条展开日志的操作。
  3. 如果任务失败，先定位执行、认证、工具或测试的具体错误，再决定是否重跑。
  4. 要停止任务，在 Details 底部选择 Cancel session 并确认。停止后的会话不能直接恢复；检查已产生的提交和评论。

网页 / Runner Flow 的会话在项目中查看；IDE 软件开发流程也有本地扩展的 Flows → Sessions。不要把 Chat history 与所有平台任务列表视为同一个入口。

操作依据：会话查看、取消与交互 · 固定 19.3.3 文档 ↗

操作依据：19.3 会话侧栏任务计划 · 固定 19.3.3 文档 ↗

02 · 需要人检查的流程，明确加入检查点

Custom flow 如果包含 HumanInputComponent，执行到检查点会等待输入。打开对应 Session，检查已做动作与下一步，使用 Approve、Reject 或 Modify 响应。没有加入这种组件的任务流，不会因为提示词写了“谨慎”就自动在指定步骤暂停。

  1. 用 Flow Creator 说明希望在哪个写入步骤之前暂停。
  2. 在生成 YAML 中检查实际包含的检查点，并在测试项目运行一次。
  3. 先选择 Modify 验证反馈分支，再用 Reject 验证停止；不要第一次就接入生产级写操作。

操作依据：人工检查点的条件与响应 · 固定 19.3.3 文档 ↗

03 · Restricted：在顶层群组内共享能力

可见性分享范围使用方法
Private管理项目内部先完成单项目试点。
Restricted同一顶层群组中的项目从项目 AI → Agents / Flows 创建或编辑时选择。
Public实例范围内可见仅发布确定适合广泛复用的配置。

19.3 新增 Restricted，受 ai_catalog_internal_visibility 功能标志控制且默认启用。若某个 public 项已经被群组外项目启用，不能直接缩小成 Restricted。可见性不会替代运行用户对数据的权限。

04 · 先观察消耗，再配置上限

上游私有化管理员可进入 Admin → GitLab Credits 查看用量。用户明细可能需要单独开启展示；自动流程可能以非人类主体计量。检查实际任务与用量关联，不只看总余额。

  1. 先用同一组小任务做几轮试点，记录成功率、返工、CI 结果与额度变化。
  2. 对上游订阅级 on-demand 上限，由 billing account manager 进入 Customers Portal → GitLab Credits dashboard → Spend controls → On-demand credit cap 设置并保存。
  3. 19.3 的默认用户上限与用户覆盖值主要通过 GraphQL API 配置，参考固定版本的 upsertFlatUserCap、upsertUserBudgetCapOverrides，并先查询当前设置。不要把 19.4 的新 UI 菜单倒推到 19.3。
  4. 触达上限后，相关能力会暂停；先确认是个人限制、订阅限制还是余额问题，再由有权限的管理员调整。
额度上限的含义要看类型订阅级上限控制 on-demand，不能理解成“所有 AI 用量的即时硬停止”。计量与执行存在延迟，包含额度也有单独规则。极狐的合同、门户和额度机制需单独确认，不能直接在 JH 上照搬上游购买步骤。

操作依据：19.3 Credits 上限、用量与 GraphQL 入口 · 固定 19.3.3 文档 ↗

05 · 自部署模型：先验证网关，再绑定功能

  1. 按部署方案准备带 Agent Platform 服务的 AI Gateway，并确认 GitLab 与执行环境到网关和模型端点的网络。
  2. 管理员进入 Admin → GitLab Duo → Change configuration，设置 Local AI Gateway URL。私有地址若被拦截，应按实例出站策略配置允许范围。
  3. 进入 Configure models for GitLab Duo → Add self-hosted model，填写 deployment name、model family、endpoint、必要的 API key 与 model identifier。
  4. 保存后为目标功能选择对应模型，先验证一次简单 Chat 和一个小编码任务，再扩大使用。
  5. 记录超时、工具调用、测试执行和失败恢复情况；“模型端点能返回一段文字”还不足以说明完整 Agent 流程兼容。

操作依据：网关、模型注册与功能配置 · 固定 19.3.3 文档 ↗

06 · 19.3 的上游模型变化如何理解

上游 19.3 提供 Amazon Bedrock Mantle 的 Beta 支持，并弃用 Devstral 2，给出 Mistral Medium 3.5 等支持路径。这是上游的支持矩阵变化，不证明 striding JH 已配置这些云服务或模型。

  • 使用 Mantle 时，先核对支持的 serving platform 文档、网关版本和该功能的模型绑定；它不是只改一个模型名字。
  • 如果当前配置仍引用已弃用模型，先在测试项目验证替代模型的工具调用与结果，再切换业务项目。
  • 极狐实际模型名称、国内服务和自部署支持范围以厂商文档与实例配置为准，不根据上游默认模型猜测。
