03 / PUT IT TO WORK

两条接入路线，各自解决什么问题

以下为试点建议。先选一个小仓库与可验收任务，观察结果再扩大使用范围；不预设节省工时或自动合并效果。

路线 A · 现有 coding agent

MCP 提供项目与协作上下文

适合已经在用本地或 IDE Agent 的开发者。

  1. 管理员确认并开启该实例的 MCP 服务。
  2. 在支持 MCP 的客户端中连接 https://<实例域名>/api/v4/mcp，完成 OAuth 授权。
  3. 先测试读取一个可访问的 MR，确认差异和讨论可取到。
  4. 让 Agent 在本地修改、执行测试，再提交 MR。

客户端的模型账号与费用另计；MCP 本身不提供模型，也不要求 Alfred 持有 Agent 凭据。19.3 的工具范围以实例实际返回为准。

查看接入与管理员条件 ↗
路线 B · GitLab 原生 Agent

Duo 在 Issue / MR / CI 内执行

适合希望由平台组织任务、执行和协作的团队。

  1. 确认私有化订阅、Duo 使用权与 Credits 规则。
  2. 配置 AI 网关、模型连接和实例级开关。
  3. 为群组和项目启用目标流程，确认服务账号权限。
  4. 配置所需 Runner、镜像和工具链，发起一个小任务。

“19.3.3 JH 已安装”不说明以上配置已完成。私有化的可用性应以许可证与合同为准，不能套用 JihuLab.com 基础版政策。

先说明现有实现和计划，再修改代码。

04 / ALFRED WORKFLOW

master 能适配几个大版本？

评估基线：master 的 ac6a5cc。结论：14–19 共六个大版本的代表性源码具备核心接口与路由，预期兼容；没有真实服务器联调认证。

每个大版本只检查所列代表版本，不保证所有小版本、私有补丁与部署配置。CE 上游检查不能替代 JH 实机验证。未发现需要停留在旧版的证据，因此不执行“仅旧版兼容时打 tag”的分支，也不把未经联调的版本标成已认证。

兼容依据

  • 使用 GET /api/v4/projects，通过请求头传 PAT，使用 membership 和偏移分页。
  • 搜索和克隆依赖的名称、路径、Web 与克隆 URL 字段在基础项目实体中保留。
  • GET /api/v4/user 用于个人用户名；dashboard 与 preferences 路由在所查源码中保留。
  • 项目子页面使用 /-/ 路由。页面是否可访问仍取决于权限与是否启用该功能。
查看逐版本源码链接与机器结果 ↗

本次可直接改善的地方

  • 项目列表增加 simple=true，保留所需字段，减少完整项目配置的传输和缓存。
  • Graph 原先写死 main；改用 Git 的 HEAD 引用，避免依赖默认分支名称。
  • 继续复用一套 API v4 逻辑，无需按 GitLab 大版本复制实现。
  • AI 交给 MCP 或 Duo 接入；Alfred 继续负责导航与复制克隆地址。

在 striding 上完成最终确认

glhostlist                 # 查看现有配置和刷新状态

gl <已知项目>              # 验证搜索、打开与 SSH / HTTP 克隆地址复制
gl my striding             # 仅当 profile 名称确实是 striding 时使用

再检查个人页面与项目的 Pipelines、Issues、MR、Members、Graph、CI/CD 设置。Graph 至少覆盖默认分支为 main 与 master 的项目。401 优先检查令牌有效期及权限；403 核对实例访问策略。无需为升级重复添加同一 host。
